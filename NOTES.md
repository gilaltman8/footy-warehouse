# Design decisions

- [Day 0] Databricks Free Edition, not BigQuery — BigQuery's card-free sandbox blocks DML (no MERGE) and expires tables after 60 days — at 100×: a paid workspace with cluster policies and budgets.
- [Day 0] Devcontainer on GitHub's default universal:2 image, not python + Docker feature — the feature build broke twice (Debian trixie dropped moby; an expired Yarn apt key) — lesson: pin base images and prefer maintained images over stacking installers; at 100×: a custom image built and tested in CI.
- [Day 1] Raw keeps every column as STRING (except match_date, _loaded_at) — casting is staging's job, so a bad value never fails a load — at 100×: same rule, plus schema-drift alerts.
- [Day 1] Raw load = DELETE the (season, league) slice + COPY INTO … force=true — idempotent per slice; force is needed because COPY INTO otherwise skips a file it already loaded, leaving the slice empty — at 100×: one atomic INSERT … REPLACE WHERE so readers never see an empty slice (DESCRIBE HISTORY v1 shows that window).
- [Day 1] Exit code 1 only if every league fails; one missing league logs a warning — Airflow reads the exit code as success/failure — at 100×: per-league tasks with their own retries.
- [Day 1] Parquet schema declared explicitly (pyarrow) — pandas 3 wrote text as large_string and Delta rejected the COPY — lesson: never trust library defaults at a system boundary; at 100×: pin versions and contract-test the file schema in CI.
- [Day 2] dbt-core 1.12.3 + dbt-databricks 1.12.5; YAML in 1.12 style (data_tests, arguments:, source config:) — zero deprecation warnings — at 100×: pin in requirements and upgrade on a branch with CI.
- [Day 2] stg_matches is a VIEW — cheap, always reflects raw, no state to backfill — at 100×: materialise as a table if many marts read it and the reads get slow.
- [Day 2] Dedupe on (match_date, home_team, away_team), latest _loaded_at wins — a corrected re-load replaces the old row — at 100×: the same rule, enforced by the unique test on match_key.
- [Day 2] cast for goals, try_cast for the rest — missing goals mean a broken file and must fail loudly; missing shots or odds are normal in older data — at 100×: the same split, logged as a data contract.
- [Day 2] match_key = hash(date, home, away), no season — a date plus two teams is already unique — at 100×: same key; the unique test is the grain check.
- [Day 2] Profile reads host, path and token from env vars; dbt init ran with --skip-profile-setup so the token was never written to a file.
- [Day 3] dim_team = every team seen in any loaded season (145), not one season's 120 — keys are hashes of the name.
- [Day 3] fct_match is incremental MERGE on match_key, watermark = max(_loaded_at) — proved: reload of 25/26 E0 → DESCRIBE HISTORY MERGE numSourceRows 380, updated 380, inserted 0; count 380 before and after; incremental count = full-refresh count (4,953).
- [Day 3] Watermark weakness: a reload with an older _loaded_at would be missed → lookback var (default 3 days), off with --vars '{lookback_days: 0}' when exact metrics are needed — reprocessing is harmless because the MERGE is keyed.
- [Day 3] Delta MERGE writes a deletion vector instead of rewriting files; dbt-databricks runs OPTIMIZE after each build because of liquid clustering (2 files → 1).
- [Day 3] Old record changes: corrected Forest v Bournemouth (17 Aug 2024, 1–1 → 2–1) in raw with a new _loaded_at → incremental run with lookback off → MERGE numSourceRows 1, updated 1, inserted 0 → Forest 65→67, Bournemouth 56→55. Undone by reloading the real file, not a reverse UPDATE.
- [Day 3] Counterfactual: a match_date watermark would be 2026-09-20, so the 2024 correction would be skipped forever, silently. The watermark must be on when I received the row, not when the event happened.
- [Day 3] Interview answer (mine): "My watermark is on load time, not event time. A corrected old record gets a new _loaded_at, so the next incremental run picks it up and the MERGE updates that one row. I tested it: one 24/25 correction, one row updated, and the league points moved by exactly +2 and −1."
- [Day 4] fct_team_match unpivots each match into two team rows (2× rows, tested); union all matches columns by position, so the away CTE mirrors the home CTE's order exactly.
- [Day 4] Form = rows between 5 preceding and 1 preceding — the current match is excluded (no leakage); partitioned by team only, so form carries across seasons; match_key breaks date ties for a deterministic order.
- [Day 4] Named windows: Databricks can't extend a window name with a frame (over (w rows …) is a parse error), so each frame lives inside its own named window.
- [Day 4] Validation against an outside source: computed 24/25 PL table matches the official one exactly (Liverpool 84 … Southampton 12, all tie-breaks). Balance tests: wins = losses and goals for = against in every league-season.
- [Day 3] Schema evolution: Referee added to the RENAME contract → ddl() ALTERs the raw table additively (warned once, silent on re-runs) → stg + fct carry it → fct_match got the column via on_schema_change=append_new_columns, no rebuild.
- [Day 3] New column ≠ filled history: after the change only 26/27 E0 had referees. Backfilled by reloading slices (incremental MERGE, resumable, keeps time travel), not --full-refresh (rewrites the table, resets history — a maintenance window at 100×). Result: 2,009/2,009 English matches have a referee.
- [Day 3] append_new_columns only handles additions. A column that changes type or is removed needs a full refresh or an explicit migration — additive is the only automatic direction, deliberately.
- [Day 5] Every model and column documented (doc blocks for shared definitions); checked against catalog.json, i.e. against the columns that really exist, not just the YAML.
- [Day 5] ci target built by hand once: same code into footy.ci_staging / ci_marts via the schema macro — what CI will run on every PR.
- [Day 5] sqlfluff 4.3 with the dbt templater: 100 style fixes, dbt build still PASS=42 afterwards (never trust an auto-fix without the tests). Excluded ST06 (reorders SELECT columns — would break the union-by-position in fct_team_match), RF04 (renaming result/position changes the contract), AL03.
- [Day 5] Unit test on fct_team_form: 7 hand-made rows where a one-row leak changes the answer. Proved it catches the bug: widening the frame to include the current row failed with t1 NULL→3 and t2 3→4; restored → pass. It checks matches_in_window too, because one row (t3) got the right points by coincidence.
- [Day 5] pytest on parse_match_date: both year formats, day-first (03/04 = 3 April), bad values → null not crash. Data tests find bad data; unit tests find bad logic, before it meets data.
- [Day 6] Airflow 3.2 via Astro CLI (Runtime 3.2-6, Python 3.13): 5 containers — postgres (metadata), scheduler (runs tasks), dag-processor (parses DAG files), api-server (UI), triggerer (deferred waits); db-migration runs once and exits.
- [Day 6] dbt + ingest libraries in a separate venv inside the image (tools_venv), dbt pinned to 1.12.3 = what I tested locally — Airflow and dbt pin conflicting libraries. dbt target/logs go to /tmp in the container so it never writes into the mounted repo.
- [Day 6] Repo folders are mounted into scheduler/dag-processor/triggerer (docker-compose.override.yml): edit a model, the next run uses it — no image rebuild. Secrets reach the containers via airflow/.env (git-ignored); the container's dbt profile defaults to target prod.
- [Day 6] Verified from inside the scheduler container: dbt debug --target prod → All checks passed (git added to the image via packages.txt). Unpausing the example DAG created a scheduled run immediately — why my DAG will use catchup=False.
- [Day 7] footy_pipeline DAG: 6 loads → dbt source freshness (gate) → dbt build --target prod; retries 2 with exponential backoff, on_failure_callback, execution_timeout 30 min on dbt_build, catchup=False, max_active_runs=1 (a second run would delete+reload the same slices), season from params else Variable, read at run time.
- [Day 7] INCIDENT on the first run: 6 parallel loads into footy.raw.matches → 1 succeeded, 5 failed with COPY_INTO_DUPLICATED_FILES_COPY_NOT_ALLOWED ("duplicated files were committed in a concurrent COPY INTO"). COPY INTO tracks loaded files per table, so concurrent COPY INTOs into one table conflict — row-level concurrency does not cover it. The DELETEs had committed → 5 of 6 26/27 slices empty in raw.
- [Day 7] Contained by the DAG: dbt_build depends on all six loads, so prod never saw the half-loaded raw. The freshness gate would NOT have caught it (newest _loaded_at was fresh) → Day 11: per-slice row-count check.
- [Day 7] Fix: Airflow pool raw_matches_writer with 1 slot for the load tasks — six tasks keep their own retries/logs, but one writer at a time. Retries (try 2, running under DAG version v2 with the pool) reloaded every slice: D1 36 · E0 50 · E1 95 · F1 45 · I1 50 · SP1 69. At 100×: stage per-slice data and commit once (single writer), or INSERT … REPLACE WHERE per slice.
- [Day 7] Airflow tags subprocess stderr as ERROR → success lines looked like errors; load_raw now logs to stdout. New DAG files wait up to 5 min for the folder scan → astro dev run dags reserialize. Airflow 3 runs at the cron time (not at interval end) and versions DAGs — each try records which DAG version it ran.
- [Day 7] INCIDENT 2 (found by the break test): Variable set to season 9999 → football-data.co.uk answered with HTTP 200 and the 1998/99 files → load_raw trusted the status code and loaded 1,678 matches as season '9999'. Five tasks GREEN = silent success. Only E1 failed (its 1998/99 file has a malformed line: Expected 21 fields, saw 38), and that alone kept dbt_build from pushing it into the marts. Prod saved by luck, not design; prod_staging (a view) did show the rows.
- [Day 7] Fix in three layers: (1) input — season_window() rejects anything that is not two consecutive years, before any network call (9999 → exit 2); (2) content — dates_in_season() refuses to DELETE/load a slice whose match dates fall outside 1 Jul–30 Jun of that season; (3) warehouse — dbt test assert_match_date_in_season, proven on the contaminated data (FAIL 1678) and on clean data (PASS). Cleanup: DELETE season '9999' → 1,678 rows. pytest 5 passed.
- [Day 7] Lessons: an HTTP 200 is not proof of correct data; validate before anything destructive; a config change left in place breaks the next scheduled run (06:00 run used 9999 at run time); on_failure_callback fired once because only one task failed — it alerts on failures, not on wrong data. Recovery run: all loads try 1, serialised by the pool (~11 s apart), 2 min 41 s, prod 4,953 / 0 bad rows.
- [Day 7] Codespaces: forwarded ports returned 404 after a resume/machine change (curl inside = 200, API log showed no browser requests) → known bug, fixed by toggling port visibility Public → Private. Airflow 3: manual triggers have no logical date — my DAG takes scope from params/Variable, so it is unaffected. Airflow versions the DAG file, not the code it calls (loader changes → git, not DAG version).
- [Day 8] Backfill = the same DAG with a param: triggered season 2324 and 2223 from the trigger form (Single Run, not Airflow's date-range Backfill — my data is keyed by season, not date). Predicted before running: 2,304 + 2,378 (Ligue 1 went from 20 to 18 teams in 23/24) → fct_match 4,953 → 9,635, exactly. Guarded loader accepted both; it would reject 1920 (COVID season ran into Aug 2020).
- [Day 8] catchup=False ≠ "run once": after two days asleep the scheduler ran the pending 2 Oct slot, then jumped to 4 Oct, skipping 3 Oct. Harmless here (each run reloads the whole season); data loss for a one-day-per-run pipeline.
- [Day 8] HttpSensor site_available first in the graph, mode="reschedule", poke_interval 5 min, timeout 1 h. Season 2728 (valid code, file not published) → Up For Reschedule after 0.38 s holding a slot; every load stayed No Status. poke mode would hold a worker for the whole wait. Adding the task made DAG version v3; older runs keep their v2 structure in the grid.
- [Day 8] Config as code: airflow_settings.yaml (Variable footy_current_season, pool raw_matches_writer, connection football_data) applied on every astro dev start, committed (removed from Astro's default .gitignore — it contains no secrets). The token stays in .env. Skipped a footy_catalog Variable: config nobody changes is complexity without a reason.
- [Day 9] CI on GitHub Actions (dbt_ci.yml): python-tests → build (sqlfluff lint + dbt build --target ci, every model/test into ci_*) → deploy-docs (main only, dbt docs → GitHub Pages: gilaltman8.github.io/footy-warehouse). profiles.ci.yml holds only env_var() — no secret in the repo. Versions pinned to what I tested locally (dbt 1.12.3 / databricks 1.12.5 / sqlfluff 4.3.0), runner pinned to ubuntu-24.04 after GitHub announced ubuntu-latest → 26 — "latest" is not reproducible. First deploy failed with 404: Pages source wasn't set to GitHub Actions.
- [Day 9] Branch protection on main: required check "build". PR #1 broke accepted_values on purpose → build red: FAIL 1 (accepted_values returns one row per distinct bad value, not per bad row), PASS=15, SKIP=28 — dbt built nothing downstream of the failed staging test; merge blocked.
- [Day 9] Found a real CI trap: after the revert, the PR changed zero files → the paths filter skipped the workflow → the required check never reported → the PR would wait forever. Fixed by removing the paths filter from pull_request (kept on push). Rule: a required check must always run. PR #1 history = red → revert → CI bug fixed → green → merged.
- [Day 10] Rebuilt dev before the notebook: dev_marts was still at Day 5 (4,953 matches) because 23/24 and 22/23 were backfilled to prod only. dbt build PASS=44; fct_match MERGE numSourceRows 9,635 / updated 4,953 / inserted 4,682 — the 3-day lookback reached past the Day 1 load, so every old row re-qualified and only the two backfilled seasons were inserts. Lesson: when only the orchestrator runs prod, dev drifts; check counts before trusting a dev read.
- [Day 10] PySpark notebook (notebooks/h2h_spark.py): h2h and home_advantage from the dbt marts, written back to Unity Catalog with saveAsTable — 4,008 and 602 rows, identical to the same aggregation in SQL. Same Delta tables, two engines: that is the lakehouse claim. count() read 0 rows — Delta answers it from per-file stats in the transaction log.
- [Day 10] Plan Q1 (stages, shuffle): 4 stages (3 map stages + result). One real shuffle: hashpartitioning(team_key, opponent_key) for the groupBy. A partial aggregate before it cut 19,270 rows to 4,008 on the reading worker, so only 169 KB crossed the shuffle, 0 bytes spilled — SQL Server's Partial Aggregate → Repartition Streams in a parallel plan. Photon gotcha: not every Exchange is a shuffle — SinglePartition + EXECUTOR_BROADCAST is a broadcast; read the Arguments line.
- [Day 10] Plan Q2 (AQE): explain says isFinalPlan=false — that is the plan before running. AQE re-plans after each stage finishes (profile: "Execution 4 of 4") using real sizes: it coalesced the shuffle from 16 partitions to 1 (AQEShuffleRead) because 169 KB doesn't justify 16 tasks. Its other two levers: switch a sort-merge join to broadcast once a side turns out small, and split skewed partitions.
- [Day 10] Plan Q3 (join): both joins to dim_team (160 rows) are broadcast hash joins — the small table is copied to every worker and the 4,008-row side never moves. The optimizer reordered them (code joins team first, plan joins opponent first; inner joins commute). At 100 GB on both sides: sort-merge join, both sides shuffled on the key, and skew on hot keys becomes the risk.
- [Day 10] Plan Q4 (why Spark at all): not for this data. The h2h write took 30 s wall; every aggregate, shuffle and join ran in 4–16 ms, while each scan took ~6.4 s (cold start + I/O) — the job is pure overhead. In SQL it is four lines. Spark earns its place for logic SQL can't express, reuse in Python/ML, UDFs, streaming, or data past one warehouse's economics. I wrote it to read plans honestly, not because the volume needed it.
- [Day 11] dbt_expectations 0.10.10 (+ dbt_date 0.21.0): home_goals 0–15, odds_home 1.0–100 when not null, row count ≥ 1,500 per season excluding the season in progress → 39 data tests, PASS=47. Proved it bites: --vars current_season 9999 → FAIL 1 (2627 with 345 rows). dbt reports a failing test as ERROR=1 in the summary line.
- [Day 11] Run log: fct_match post_hook = create table if not exists + insert (logged_at, target, model, row_count, invocation_id) into <catalog>.<schema>.pipeline_log. The guide's version had no create, so the first build, CI (ci_marts) and Airflow (prod_marts) would all have failed. row_count is the table total, not the change — the change lives in DESCRIBE HISTORY. Same instinct as the sync-failure log I built at a lending fintech.
- [Day 11] DESCRIBE HISTORY: an update-only MERGE uses deletion vectors — the 5,027 updated rows go to a new 169 KB file and the old copies are marked deleted, 0 files rewritten — so dbt's post-model OPTIMIZE compacts 2 files → 1 and commits a version. Day 10's v22 also inserted rows, rewrote the single file, and left OPTIMIZE nothing to do — that is why it had no OPTIMIZE row.
- [Day 11] Time travel has two edges: older than delta.deletedFileRetentionDuration (168 h) is refused even if files still exist (v21 at 7 d 17 h), and a timestamp after the latest commit is refused too (no rounding to "now"). Rollback window = 7 days — a bad run found on day 8 can't be undone this way.
- [Day 11] Freshness: latest match 2026-09-20, 17 days behind. The source file itself still ends on 20 Sep (50 PL rows, HTTP 200 after a www → non-www redirect), so the source went silent; and raw _loaded_at stops at 4 Oct because Airflow only runs while the codespace is up. Two signals: _loaded_at says whether we ran, MAX(match_date) says whether the world moved. Neither produces a failed task — that is why silence is the dangerous failure.
- [Day 12] The Day 4 claim "my 24/25 PL table equals the official one" is now a test, not a sentence: seeds/pl_2425_official.csv (the published final table) + tests/assert_league_table_matches_official.sql (full outer join on team, fails on any difference in position incl. tie-breaks, points or goal difference). Proved it bites: Arsenal 74 → 75 in the seed → FAIL 1; restored → PASS. Anyone can read both files and see it pass in CI, with no workspace.
- [Day 12] README: 15 design decisions (decision → why → at 100×), data contract checked line by line against load_raw.py (RENAME map, additive ALTER + warning, missing → NULL), and an Evidence table whose numbers are dated. Lineage image drawn from manifest.json by docs/make_lineage.py, so it is reproducible, not a screenshot. Public repo rule: no former employer's name — "a lending fintech".
- [Day 12] Pages actions → v5 (Node 24) cleared the Node 20 warnings. Deploys then took 4–6 min: deployment created in 2 s, then 11 polls of "updating_pages" over 4.5 min — GitHub's Pages backend, not the action. The real bug was mine: concurrency cancel-in-progress: true on main cancelled run #7 mid-deploy when #8 queued. Now it cancels superseded PR builds only.
